# 夜裔幸存者 · 神器合成提示 UX 设计分析

> 文档用途：玩家反馈「记不住『武器 + 被动 → 神器』合成路径」，并自发提议「升级卡选被动时，被动卡下方显示与什么武器可合成什么神器」。本文抽取项目**真实合成规则**（事实基础），评估该方案，调研同类游戏，给出 1–3 个可落地方案与 UI 规格。
>
> 项目：Night Survivors v1.9 · Vite + Canvas2D · 纯设计分析（不含实现代码）
> 事实来源：`src/data.js`(RECIPES/ARTIFACTS/WEAPONS/PASSIVES)、`src/evolution.js`(findEvolvableRecipe/performEvolution)、`src/weapons.js`(addArtifact 神器注入)、`src/upgrade.js`(升级卡 UI)、`src/game.js`(onChestOpened 进化触发)、`src/ui.js`(进化横幅/图鉴)

---

## 0. 关键前提：本作进化是「自动触发」而非「玩家选择」

这是设计本方案的**第一性前提**，直接决定提示该回答哪类问题。

- `src/game.js:382 onChestOpened()`：开宝箱时调用 `findEvolvableRecipe(player, weapons)`。
- 若命中配方（满级武器 + 已持有该被动 + 尚未拥有该神器），**立即自动 `performEvolution`**，无玩家确认；随后 `ui.showEvolutionBanner()` 弹出「进化成功」横幅（`src/ui.js:281`）。
- 进化发生时原武器从 `player.weapons` 被移除，神器以 `{ id, artifact:true }` 注入（`src/weapons.js:120 addArtifact`）。

**推论**：玩家在升级卡上**不需要「决定要不要进化」**，只需要「知道该凑哪把武器 + 哪个被动」。因此提示的核心价值是 **build 规划 / 目标牵引**，而不是「进化时刻的决策辅助」。一个只告诉「配方是什么」的提示，只解决了问题的一半——另一半「我现在离进化还差什么 / 我是不是下一箱就进化了」当前完全没有被满足。

## 1. 真实合成规则抽取（事实基础）

### 1.1 进化判定条件（`src/evolution.js:4 findEvolvableRecipe`）

一条配方可被进化，当且仅当**同时满足**：

1. `weaponSystem.weaponLevel(r.weapon) >= WEAPONS[r.weapon].maxLevel` —— 武器**满级**（本作所有武器 `maxLevel = 5`）；
2. `player.passives.has(r.passive)` —— 玩家**已持有**该被动（任意等级均可，不要求满级）；
3. `!weaponSystem.hasArtifact(r.artifact)` —— 玩家**尚未拥有**该神器。

> 注意：被动**不要求满级**，只要求「持有」。这是玩家常踩的认知坑——以为要先把被动升满。

### 1.2 完整「武器 + 被动 → 神器」映射表

取自 `src/data.js:465 RECIPES`（共 10 条，对应 10 个神器）：

|---|---|---|---|---|---|

| 2 | 圣水洗礼 `holywater` | 引力宝珠 `magnet` | 圣洁吞噬 `devour` | normal | — |

### 1.3 多对多结构分析（直接影响提示文案长度）

- **一把武器对应多个被动**：`blade`（→storm / →crimson）、`lightning`（→stormcall / →tempest）。
- **一个被动对应多个武器**：`boots`（→storm / →tempest / →eternalwhip，3 条）、`heart`（→spiral / →sepulcher）、`tome`（→stormcall / →crimson / →matrix，3 条）。
- **参与配方的被动仅 5/13**：`boots / magnet / heart / tome / greed`。**其余 8 个被动无任何配方**：`guard 钢铁意志、regen 血色再生、critrate 致命专注、critdmg 毁灭之刃、shield 幽能屏障、shieldregen 灵能回响、armor 暗夜铠甲、dodge 魅影身法`。
- **全部 10 把武器均至少有一条配方**。
- **隐藏配方 2 条**：#5 `crimson`、#6 `tempest`（稀有度 `hidden`）。图鉴 `buildCollectionData`（`src/evolution.js:37`）对未解锁的 hidden 神器显式遮罩为「???（隐藏配方，自行探索）」——本作**刻意保留秘密进化**，提示方案必须尊重该意图。

### 1.4 ⚠️ 系统级隐患：「首条命中即进化」导致多对多实为「顺序互斥」

`findEvolvableRecipe` 按 `RECIPES` **数组顺序返回第一条满足的配方**。后果：

- 若玩家 `blade` 满级 + 同时持有 `boots` 与 `tome`：开箱时先命中 #1（storm），`blade` 被移除 → #5（crimson）**永远无法触发**。两条 blade 配方互斥。
- `lightning` 同理：#4（stormcall）先于 #6（tempest）命中，两条互斥。

**对提示设计的影响**：不能在被动卡上承诺式地写「选我可合成 storm / tempest / eternalwhip（三选一）」——因为若玩家已持有冲突的满级武器+被动，实际进化由数组顺序唯一决定，文本会误导。提示的「就绪」状态必须以引擎同一函数（`findEvolvableRecipe`）为唯一事实源，避免漂移。

## 2. 用户方案评估：「被动卡下方显示合成提示」

> 用户原话：升级卡选择被动时，被动卡下方简短显示「与什么武器可合成什么神器」。

### 2.1 优点

- **方向正确**：在决策现场（选被动）补给配方知识，命中「记不住路径」的痛点；实现成本低（仅在 `src/upgrade.js:155 describe()` 的 passive 分支追加一行 + CSS）。
- **契合心智模型**：玩家此刻正纠结「这个被动值不值得拿」，告知其终局用途，直接辅助 build 规划。
- **复用既有三栏结构**：当前卡为 `[图标] [标签/名称/描述] [选择按钮]`，在描述下方追加一行不破坏布局。

### 2.2 不足与风险（逐条）

1. **只答了「配方是什么」，没答「我离进化还差什么」**。因进化是自动的，玩家更需要的是「我下一箱是不是就进化了 / 我还缺哪把满级武器」，而朴素方案不提供就绪态。
2. **缺「武器持有状态」会误导**。写「血之飞刃 + 本被动 = 千刃风暴」但玩家根本没拿过 `blade`，提示变成纯图鉴、无行动价值，反而增加认知噪音。
3. **对老玩家冗余 / 选择焦虑**。每轮每张被动卡都挂一行配方， veteran 视其为 clutter；新手则可能因看到 3 条 boots 目标而分析瘫痪。
4. **泄露隐藏配方**。#5/#6 是 `hidden`，若直接写出神器名，破坏图鉴「自行探索」的刻意设计（与 `buildCollectionData` 的遮罩逻辑矛盾）。
5. **移动端纵向空间紧张**。`touch-device` 下卡片改为竖排满宽，叠加多目标（boots 有 3 条）易溢出或挤压按钮。
6. **多目标冗长**：boots 一行塞 3 个目标 + 武器名，远超「简短」预期，需截断策略（「等+N」）。

### 2.3 结论

**用户方案方向成立、性价比高，但当前描述欠精确**：它只解决「配方可见性」，未解决「就绪可见性」，且未处理隐藏配方/多目标/ veteran 冗余。建议**保留其「被动卡内提示」的落点，但升级为「就绪徽章 + 精炼配方行」双态**（见 §4 推荐方案）。

## 3. 同类游戏调研（合成 / 进化提示 UX）

| 游戏 | 进化触发方式 | 合成提示 UX | 可借鉴点 |
|---|---|---|---|
| **Vampire Survivors** | 武器满级 + 持特定被动 + 开箱（宝箱/ Boss 箱）自动进化 | 无卡内提示；依赖**图鉴(Collection)**查配方；满足条件后底部弹「Evolutions Ready」预警横幅；暂停菜单列武器等级与进化状态 | 「就绪预警横幅」+「图鉴查配方」二分法：决策时不打扰，就绪时强提醒 |
| **20 Minutes Till Dawn** | 武器 + 特定 relic 组合进化 | 卡面描述升级效果；**技能树/图鉴**揭示组合；卡内不直接标组合 | 轻量、靠探索；适合配合外部图鉴 |
| **Soulstone Survivors** | 法术 + 被动，技能树觉醒 | **技能树中显式标注 synergy / 觉醒节点**及其前置依赖；hover 出详情 | 「前置依赖可视化」：在成长树上把组合关系画出来 |
| **Brotato** | 无武器+被动进化；走**标签 synergy**（装备/武器带 Melee/Ranged 等 tag，同类叠加加成） | **卡面用彩色 synergy 标签**；当前已拥有的同类 tag **高亮变绿** | 「当前相关即高亮」——只强调此刻与你 build 有关的项，不堆全部信息 |

### 3.1 跨游戏规律提炼

- **没有一款**在升级卡里把「完整配方树」硬塞给玩家；主流做法是**「图鉴查全貌 + 就绪时强提醒」**二分。
- **Brotato 的「相关即高亮」** 是最适配本作的解法原型：不在卡上罗列所有配方，而是**只为「此刻与你相关的那条」高亮**。
- **VS 的「就绪横幅」** 证明「自动进化」类游戏必须在就绪瞬间给一个强信号——本作已有 `showEvolutionBanner`（进化后），但**进化前/凑齐瞬间缺一个「即将进化」预告**。

## 4. 更优方案（推荐组合）

给出 4 个候选，按落地优先级排序；**推荐 A+B 同发**，D 作为结构性长期修复。

### 方案 A —「进化就绪」金徽章（★ 主推，落地第一）

- **思想**：借鉴 Brotato「相关即高亮」+ VS「就绪强提醒」。**只在被动卡「凑齐即进化」时出现徽章**，把抽象的配方变成「现在选我，下一箱就进化」的行动信号。
- **触发条件（伪代码，单一事实源）**：
  ```js
  // 复用引擎函数，避免与 findEvolvableRecipe 漂移
  const ready = findEvolvableRecipe(player, weapons);
  const isReadyForThisPassive = ready && ready.passive === option.id;
  ```
  即对当前被动卡，当且仅当引擎下一次开箱**实际会**走这条配方时，渲染徽章。多配方冲突时（§1.4）自动只高亮真正会触发的那条，无误导。
- **UI 落点**：徽章置于 `.upgrade-card` 顶部（图标左上角叠加 / 或 `.uc-body` 最上方），金色描边 + 轻微脉冲动画，文案：
  `⚡ 进化就绪 · 拾箱即合成 ✨<神器名>`
  - 若目标为 **hidden 且未解锁**（crimson/tempest）：神器名遮为 `???`，保留「你即将进化某物」的悬念，与图鉴一致。
- **文案规格**：徽章单行 ≤ 18 中文字；神器名用图标+名，武器/被动不重复列出（玩家已知「持有该被动」）。
- **信息层级**：颜色最突出（金 #d4af37，呼应 `evolution-banner`/宝箱火花色），高于标签与描述。
- **认知负荷**：极低——仅在「真要进化了」出现， veteran 不感冗余（无就绪则无徽章），新手获得最强行动指引。

### 方案 B — 精炼静态配方行（用户方案升级版，落地第二）

- **思想**：保留用户「被动卡下方显示配方」的意图，但**精炼 + 尊重隐藏 + 仅对有配方的被动显示**。
- **触发条件**：被动卡 + 该被动存在 ≥1 条配方 + 当前**非就绪态**（就绪态已由 A 接管，避免重复）。
- **UI 落点**：`.uc-body` 的 `<p class="desc">` 下方追加一行 `.uc-recipe`：
  `可合成 ✨<神器> = 满级🗡️<武器> + 本被动`
  - 多目标（boots 3 条 / tome 3 条 / heart 2 条）：只列**第 1 条** + `「等 N 种」`，点「图鉴」可看全；不堆满卡面。
  - 无配方被动（8 个）：**不渲染本行**，保持卡面干净。
  - hidden 配方：神器名显 `???`，与图鉴遮罩一致。
- **文案规格**：单行 ≤ 20 中文字；**图标优先于文字**（武器/神器用 emoji 或图鉴同款小图标，减少阅读量）。
- **信息层级**：弱于徽章（次级灰/青色），属于「知识补给」而非「行动号召」。
- **认知负荷**：低–中；建议加设置开关「显示合成配方提示」（默认开，veteran 可关），兼顾两类玩家。

### 方案 C — 武器升级卡对称提示（互补，可选）

- **思想**：配方另一半在武器。当玩家选 `weapon-up` 且武器**已达/接近满级**时，在武器卡下方提示「满级后可 + <被动图标> 进化 ✨<神器>」，与 B 形成双向引导。
- **触发**：`weapon-up` 卡 + `weaponLevel(id) >= maxLevel-1` + 存在配方 + 非就绪。
- **价值**：解决「我在升武器，但不知道该顺手拿哪个被动」的盲点；与 B 构成完整闭环。

### 方案 D — 全局「进化进度」追踪条（HUD/图鉴，长期结构性修复）

- **思想**：在 `refreshLoadout()` 已有的装配栏（武器/被动槽位计数）旁，增加常驻微型进度：对每条「玩家已持武器 + 已持被动」的配方，显示 `武器 LV.x/5 + 被动✓ → 待合成/已合成`。
- **触发**：实时（每次 `refreshLoadout`）。
- **价值**：彻底解决「记不住路径」——把配方树变成随时可查的进度面板；优于任何卡内单点提示。工作量略大（需新 UI 区块），建议作为 v2.0 结构性优化。
- **参考**：本质是把 VS 的「图鉴 + 就绪横幅」合成为游戏内常驻面板。

### 4.1 推荐落地顺序

| 优先级 | 方案 | 工作量 | 价值 | 说明 |
|---|---|---|---|---|
| P0 | **A 就绪徽章** | 小 | 高 | 直接解决「自动进化」下最缺的就绪信号；单一事实源无漂移 |
| P1 | **B 精炼配方行** | 小 | 中–高 | 保留用户意图，补全配方知识 |
| P2 | C 武器卡对称提示 | 小 | 中 | 与 B 闭环 |
| P3 | D 全局进度条 | 中 | 高（结构性） | 长期根治，建议下个大版本 |

> **一句话推荐**：先做 A（就绪徽章）+ B（精炼配方行）同发——A 管「现在该不该拿」，B 管「拿了能合成啥」，二者以引擎 `findEvolvableRecipe` 为唯一事实源，零误导、低冗余、尊重隐藏配方。

## 5. 可落地 UI 规格（推荐方案 A+B）

### 5.1 DOM 落点（基于 `src/upgrade.js:177 open()` 现有结构）

```
.upgrade-card
  img.icon
  .uc-body
    [A] .uc-evo-ready        ← 仅就绪时插入（方案 A，置顶，金徽章）
    .uc-kind  (标签：属性 → LV.x)
    h3        (被动名)
    p.desc    (被动描述)
    [B] .uc-recipe           ← 非就绪 + 有配方时插入（方案 B，灰青行）
  button.uc-pick (选择)
```

### 5.2 触发与渲染规则（精确）

| 状态 | 条件 | 渲染 |
|---|---|---|
| 就绪（A） | `findEvolvableRecipe()?.passive === option.id` | 金徽章 `⚡ 进化就绪 · 拾箱即合成 ✨<名/???>` |
| 配方可知（B） | 非就绪 且 `RECIPES` 含此 passive 且目标非 hidden-未解锁 | 行 `可合成 ✨<名> = 满级🗡️<武器> + 本被动`（多目标截断「等 N 种」） |
| 配方隐藏（B 变体） | 非就绪 且 目标 hidden 且玩家未解锁 | 行 `可合成 ✨??? = 满级🗡️<武器> + 本被动` |
| 无配方 | 此 passive 不在任何 RECIPES（8 个被动） | 不渲染任何额外行 |

### 5.3 文案与字数约束

| 元素 | 模板 | 上限 | 图标策略 |
|---|---|---|---|
| A 徽章 | `⚡ 进化就绪 · 拾箱即合成 ✨{神器}` | 18 中文字 | 闪电/神器图标前置；神器未解锁显 `???` |
| B 行 | `可合成 ✨{神器} = 满级🗡️{武器} + 本被动` | 20 中文字 | 神器/武器用图标；文字仅补语义 |
| B 多目标 | 仅首条 + `等 {N} 种 ›` | 同上 | 「›」引导去图鉴 |

### 5.4 信息层级与配色

- **最高**：A 金徽章 `#d4af37`（呼应 `evolution-banner`、宝箱火花，建立「进化」视觉语言一致性）。
- **次级**：B 行灰青 `#9fc5ff`/`#7ec8ff`（与被动图鉴配色 `src/ui.js` 分类标签「被动=青」对齐）。
- **基底**：现有标签/描述不变。
- 动画：A 仅轻微脉冲（2s 循环，opacity 0.85↔1），不抢选择按钮焦点。

### 5.5 认知负荷评估

| 方案 | 新手 | 老玩家 | 冗余风险 | 误导风险 |
|---|---|---|---|---|
| 用户原案（全量配方行） | 中（信息多） | 高（每次都看到） | 高 | 中（缺武器状态/泄露隐藏） |
| **A 就绪徽章** | 低（命中即学） | 低（无就绪则无） | 极低 | 极低（引擎同源） |
| **B 精炼行** | 低–中 | 中（可关） | 低（仅相关被动） | 低（尊重隐藏） |
| A+B 组合 | **低** | **低** | **低** | **极低** |

## 6. 风险与取舍 / 已知问题

1. **「首条命中即进化」互斥（§1.4）**：多对多配方实为数组顺序唯一解。A 方案以 `findEvolvableRecipe` 为唯一事实源可规避误导；但若未来希望「让玩家在冲突时选进化哪条」，需改造 `performEvolution` 为**多候选弹窗选择**——那是独立系统任务，不在本 UX 方案范围，建议单独立项。
2. **隐藏配方泄露**：crimson/tempest 必须遮罩，与 `buildCollectionData` 一致；任何提示路径都不得显名未解锁 hidden 神器。
3. **被动不要求满级**：提示文案务必写「满级武器 + 持被动（任意级）」，纠正「被动也要满级」的普遍误解。
4. **移动端空间**：A 徽章用顶部叠加（不占纵向高度）；B 行单列截断，避免 `touch-device` 竖排溢出。
5. **veteran 冗余**：B 行加设置开关（默认开）；A 徽章因「仅就绪才现」天然不冗余。
